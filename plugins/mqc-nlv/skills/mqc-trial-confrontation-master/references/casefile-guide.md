# casefile.json 填法规程

> 这份文件管的是**怎么把卷宗读成 casefile.json**。判据在 `extraction.md` / `intake.md` /
> `layout-constraints.md`，本文件只管填法与次序，不重复法理。
> 填完先跑 `scripts/check_claims.py casefile.json`，全绿再进管线。

---

## 0. 三条贯穿全程的纪律

0. **主体目的优先** —— 这个 skill 只干一件事：出一张庭审攻防的可视化图表。
   下面三条纪律取自要件审判九步法与被告代理打法手册，吸收它们的前提是不损害这件事。
   任何一条纪律若要靠改写判定的输入来表达，那就是改坏了——改判据，不改判定。
1. **分级不拒跑** —— 材料再薄也有产出。材料成熟度只改变证明前景能推到多深，
   不改变结构：`scope.maturity` 标 L0／L1 时，争议要件的 `prospect` 一律标「待定」，
   不许下「高」或「低」这类硬判断（M2 会拦）。
2. **三标出厂** —— 每条要件带三标：法律置信 `conf_law`、证据置信 `conf_evid`、
   立场方向 `direction`。法律层面与证据层面分开评级，绝不合成一个模糊分数：
   一个案子完全可能法律上站得住而关键事实证不出，两者不得互相稀释。
3. **客观与立场物理分离** —— casefile 与图表只装客观研判。
   `case.stance` 标的是「这份推演是给谁做的」，不是打法；
   攻防着力点、诉请设计、检索方案另出，不进这张图。

---

## 1. 次序：按律师接案的动线填，不按 JSON 的字段顺序填

    ① case.stance        我代理谁 —— 原告向 / 被告向。不填，后面每条读数都没有方向。
    ② case.procedural    程序站 —— 管辖 / 主体 / 重复起诉三项必须逐项写到（P1 会数）。
                         这是防「单方材料直通全胜」的闸：先问会不会被裁定驳回起诉。
    ③ scope              材料范围 —— obtained / not_obtained / maturity。
                         手上没有的文书必须列名，后面每一处空段都要回来对这份清单（S1）。
    ④ claims             诉请固定 —— 逐条识别、分类、守边界、固定金额与构成明细。
    ⑤ case.counterattacks 攻击性防御 —— 反诉 / 抵销 / 违约金酌减 / 另案主张，单列，不入四分法。
    ⑥ parts              对抗部分 —— 请求权基础 → 要件拆解 → 四段攻防 → 两层审查。
    ⑦ case.triage        全案研判 —— 最后写，它是⑥的收束，不是开头的印象。

## 2. 逐项填法

### ① case.stance

取值只有 `原告向` / `被告向`。

同一份 casefile，两种立场的读数相反：D1 算出「提出请求的一方证不出」，
对抗辩方是好消息、对请求方是警报。所以立场不是装饰，是读图的前提。
未指明时先问律师；确需双向的，各跑一遍，**不要在一份文件里混着填**。

### ② case.procedural

一段话写清三件事，缺一不可：

- **管辖** —— 依据是什么（约定管辖条款 / 法定连结点），与受理法院是否一致。
- **主体** —— 双方是否适格，是否需要追加当事人。
- **重复起诉** —— 就同一法律关系、同一诉讼标的有无另案或已生效裁判。

这三项任何一项不过，案子在实体审理之前就结束了。先跑完这一站，再谈要件。

### ③ scope

    "scope": {
      "obtained":     ["起诉状", "证据目录"],
      "not_obtained": ["答辩状", "代理意见", "质证意见"],
      "maturity":     "L1",
      "note":         "被告尚未提交答辩状，其观点仅见于证据目录的证明目的栏"
    }

成熟度四级：

| 级 | 材料状态 | 证明前景能推到哪 |
|---|---|---|
| L0 | 口述或一段话 | 全部标「待定」，只跑法律层面 |
| L1 | 关键文书其一二（起诉状 / 合同 / 一审判决书） | 文书涉及的要件给初步方向，其余挂缺口 |
| L2 | 部分卷宗（含部分证据） | 多数争议要件给前景，少数挂缺口 |
| L3 | 完整卷宗（举证质证齐备） | 可给较实的证明前景 |

`not_obtained` 里的文书名，要和四段 `src` 里写的名字**用同一套说法**，
否则 S1 对不上。图上不为缺位立框，缺口只出现在图底的材料范围里。

### ④ claims

逐条走这四步：

**识别** —— 不看起诉状写的案由标签，从诉请形态倒推：要付款、要返还、要赔偿、要交付，
还是要解除、要确认。形态决定规范，标签不产生拘束力。

**分类** —— 填 `type`，取值见 `intake.md` 的封闭表。

**守边界** —— `type` 为「确认」或「形成」的，**不按要件拆**。
请求权基础方法锚定给付之诉；确认与形成之诉的规范结构不是「要件→给付效果」，
硬拆等于把方法用在它失灵的地方。这两类必须填 `boundary`，写明转法律关系分析法，
并说明本图只呈现双方就该形成权 / 确认对象的攻防（E1、E2 会查）。
混合诉切分处理：给付部分照常跑，确认 / 形成部分标出边界。

**固定** —— 给付钱款与给付实物必须附 `breakdown`，每项写项目、金额、依据，
合计与主张额相符。主张额低于各项加总的（协商减让、部分放弃、暂计），
差额作为一条显式的调整项列出并注明依据，不得把明细改写成凑得上的数。
取不出确定数额的（「按实际发生额」）不核算。

### ⑤ case.counterattacks

    "counterattacks": [
      {"kind": "抵销",
       "handling": "抗辩方称以其对请求方的到期债权抵销。不属四分法内的抗辩，
                    系独立的权利主张；本案抵销后仍有余额须对方支付，故应以反诉主张，
                    另交诉讼费，已向当事人说明。"}
    ]

`kind` 取值只有四个：反诉 / 抵销 / 违约金酌减 / 另案主张。

这四项**不是抗辩**：它们不否认事实、不阻却权利发生、不使权利消灭、也不是拒绝履行的抗辩权，
而是另起一条独立的权利主张。硬塞进四分法必然归错——抵销会被归成「权利消灭」，
可它针对的是全案而不是某一个要件。G1 会把混进 `response_class` 的这四个词拦下来。

`handling` 要写清走哪条路（本案反诉 / 另案起诉 / 本案抗辩），以及费用与期限。
违约金酌减尤其注意：依民法典第五百八十五条第二款是「根据当事人的请求」，
必须主动提出，法院一般不主动调整。

### ⑥ parts → claim_bases → elements

**请求权基础** —— `basis` 写规范出处，`norm_type` 分主要规范 / 辅助规范，
`verify` 写核验状态，未核验的标【待核验】并给检索方向，绝不编造条号。

**定性风险** —— `recharacterization_risk` 是这一栏里价值最高的一格。
攻要件是拆零件，攻定性是拆整条生产线：要件被攻破只影响该项主张（并联），
定性被改掉则整套请求权基础更换，管辖、举证责任、时效、金额算法同时变（串联）。
所以先看定性能不能动，动不了才下到要件层。识别真实法律关系看六件事：
给付内容、对待给付、履约方式与人员组织、风险与所有权转移时点、验收与结算方式、
以及一个诉里是否混了数个法律关系。
按 A2，这一栏只给方向，结论留空等律师填。

**要件拆解** —— 一个「有争议待证」的要件占图上一个行组。
无争议的（默示满足、隐含前提）照填，标 `dispute` 为「默示满足」，只在表里留痕，不进图。

**四段攻防** —— 主张 / 回应 / 反制 / 再回应，一律照录原文，模型只摆位置不生成主张。
每段填 `src` 写明实际取自哪份材料，限六个中文字以内的短名，全称写进表。
不得套用默认的四个文书名：对方只交了证据目录却标成「答辩状」，
就是在图上写一个不存在的文书。某段没有就填 `—`，由 S1 去查它为什么空。

**抗辩归类** —— `response_class` 走三问速判：
一问 是不是说原告讲的事实不存在 → 是则**否认**，举证责任仍在请求方；
二问 是不是说权利从来没产生过 → 是则**权利障碍抗辩**，举证责任在抗辩方；
三问 是不是说权利产生过后来没了 → 是则**权利消灭抗辩**，举证责任在抗辩方；
都不是而称权利还在只是现在可以不履行的 → **权利受制抗辩权**，举证责任在抗辩方。
`class_reason` 必须写出走过的三问路径（K3），归类拿不准的标【待核验】——
但【待核验】只表示待复核，不豁免 K1／K2／K3，校验时先剥标记再查。

**两层审查** —— `lay1` 是法律层面（不看证据，双方主张在法律上能否成立），
`lay2` 是初步研判（应主张而未主张、自陈不利事实、是否真争点）。两层不得合并。

**决定性要件** —— 这一栏是**纯客观判据的结果，不掺「对谁有利」**。
反诉部分的提出请求方是被告，三条全中即为决定性要件，只不过胜负朝己方有利；
把「决定性」跟「对我不利」混成一件事，是客观与立场混用。对谁有利填 `direction`。
重要性也不等于判据命中：某个要件再是枢纽，证明前景若不在「低」或「存疑」，判据就是不命中。
`decisive` 由三条判据同时命中才标「是」：
有争议 × 客观证明责任在提出请求的一方 × 现有证据未达证明标准。
辅助规范或标明不独立存在的（孳息、资金占用费这类从属请求）纵三条全中也不计入。
标了「是」的，`court_standard` 或 `triage` 必须落到标准表述上（D1 会查）：

> 该要件事实若维持真伪不明，由负客观证明责任的【某方】就此承担不利后果。

这是全套最锋利的一句，不得软化成「可能有点风险」。

### ⑦ case.triage

两三句话收束：定性之争在哪、要件之争在哪、哪一处决定成败、缺什么材料。
写在最后，它是⑥的结论，不是开头的印象。

## 3. 填完自查

    python3 scripts/check_claims.py casefile.json     # 全绿再往下
    python3 scripts/pipeline.py   casefile.json out

`check_claims` 不过就不要出图。它查的是能机械查的那一半：
诉请固定、抗辩归类、材料归因、边界、三标、程序站、金额核算。
查不了的那一半——请求权基础定得对不对、要件拆得全不全、双方的话对到了哪个要件——
没有机械判据，只能律师自己过一遍。**对错了整张图的结构就错**，且查不出来。
