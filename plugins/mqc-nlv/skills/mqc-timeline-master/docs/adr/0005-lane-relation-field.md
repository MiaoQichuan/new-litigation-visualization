# ADR 0005 — 两侧是什么关系由 `lane.relation` 声明，不靠猜泳道名

**状态：** 已采纳（2026-08-19）

## 背景

支付宝交易流水两侧是「支出 / 收入」，同一天既有支出又有收入是**完全正常的账目**，
75 笔流水报出 6 处「同日相反主张」，逐条回查原材料**一处都不是**对立主张。
满屏误报会把真报警一起淹掉（v1 在 `_sub` 注释里写过：会哭狼的报告没人看）。

而这条检查在诉讼材料上是准的（作者拿三份真实地图验过、四处全对，抓出了漏声明的冲突），
**所以不能削弱它，只能把不适用的材料挡在门外**。

根因：schema 里 `lanes` 的定义是「互相对读的对立两方（原告/被告）」，而 `RELAY-2` 364 行
明列泳道有三种语义 —— **谁的主张 / 哪一层主体 / 哪个程序阶段** —— 后两种没有字段表达。

## 决策

`lane` 加可选字段 `relation`，三个值取自 `RELAY-2` 的原话：
`assertion`（谁的主张，**默认**）、`actor`（哪一层主体）、`stage`（哪个程序阶段）。
只有 `assertion` 时「同日相反主张」才成立。**不填等于 `assertion`，已有地图一字不用改。**

## 否掉的替代

- **白名单：泳道名含「原告/被告/甲方/主张」才判对立。** 当场撞出**漏报**：仓库示例
  `stress-two-sides` 的泳道名是「甲公司、乙公司 / 丙公司」—— 真正对立的两方，却不含任何
  白名单字样。**漏报比误报严重**：误报是多问一句，漏报是把材料里真实存在的矛盾咽下去。
- **黑名单：泳道名含「支出/收入/付款/到账」才判不对立。** 只覆盖账目方向那一类；
  「母公司 / 子公司」「总包 / 分包」「一审 / 二审」「审理 / 执行」六个用例照样误报。
  泳道名的写法无穷，语义只有三类 —— **这是语义问题，不是字符串问题**。
- **字段与词表并存（字段优先、词表兜底）。** 留过一版，后果立刻出现：不填 `relation` 时
  契约说「等于 assertion（对立）」，而词表看到「支出 / 收入」判成不对立，
  **暗中生效的是词表**。同一件事有两个判据，必然有一个说话不算数。词表已删。

## 执行处

`check_model_output._is_adversarial` + `check_lane_labels`（标记 `[C16]`）；
schema `$defs/lane.properties.relation`（**可选**，`required` 未动）；
管线在 `stage_render` **就地组装** lane 定义（不能用 `m["lanes"]` —— 那要到更下面才赋值，
传进来是空的，于是判据退回兜底：第一版就这么错了，把 relation 从 `actor` 改成 `assertion`
误报本该回来，实测仍是 0 处，**字段成了死字段而表面上「误报消失了」**）。
`tests/run_checks.py` 四值 + 混搭 + 拿不到 lane 定义共六条，加「不许再出现词表」的检查。

## 后果

- 加了一个字段就多一处「声明了没人读」的风险，所以每加字段都要**试着把它改坏一次**
  （把 `relation` 从 `actor` 改成 `assertion`，误报必须回来）。这一条是这次最大的教训。
- 三个值不够用时（真出现第四种泳道语义）再扩，扩的时候在守卫里加一条用例。
